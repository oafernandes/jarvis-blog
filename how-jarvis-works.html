How Jarvis works

Jarvis is an AI collaborator that remembers. It's built from Claude Code, a folder of plain markdown notes, and a few small scripts. There's no server, no database and nothing secret about it. This page explains how it fits together and how to build your own.

01The idea

AI chats forget everything when you close the window. Jarvis works around that by keeping its memory in a folder of notes. It reads them when a session starts and writes to them before the session ends. An instruction file tells Claude Code that when it runs in that folder, it is Jarvis.

The setup was inspired by a Reddit post about a "second brain" assistant. Jarvis was built in its first week, mostly by asking Claude Code to build it.

Nothing to host

Claude Code, markdown files, a few scripts and one local search tool, all on one PC.

Readable memory

Every memory is a line of text you can open and edit. If you change a note, your version wins.

Versioned

Each session ends with a git commit, so "what did Jarvis know last Tuesday?" has an exact answer.

Searchable

A local search engine finds notes by keyword and by meaning.

02Architecture

PieceWhat it does
Claude CodeThe agent. At startup it reads CLAUDE.md, the operating manual, which gives it Jarvis's identity, rules and habits.
Startup hookA small script that runs when a session opens and prints the date, the task in progress, the dashboard, due promises and the last session's summary into the conversation.
Per-message hookAdds the current time to every message. If the session has been sitting open for a while, it refreshes the context, so Jarvis never works from a stale snapshot.
SkillsNamed routines: /wrap ends a session, /recall searches memory, /idea captures an idea, /evening runs the idea pipeline, and /blog made this blog.

Scheduled runsWindows Task Scheduler starts Claude Code without a window for the morning check-in, the evening idea pipeline and an overnight catch-up. These runs can read and edit notes but can't run shell commands.
Remote ControlKeeps a session available so Jarvis can be used from the Claude phone app. The phone is just a window: the work happens on the PC, with the same memory and rules.
GitEvery session ends in a commit, so the memory's history is its backup.

03Memory

The folder is organized roughly the way human memory is described: what you're doing now, what happened, what you know, how to do things, and what you promised to do later.

KindFileWhat's in it
How-toCLAUDE.mdThe operating manual: hard rules, rituals, conventions. Loaded every session and kept short.
Identitybrain/jarvis-core.mdPersonality and values. Changed only with the owner's agreement.
DashboardVAULT-INDEX.mdPriorities, active projects, last session.
Workingbrain/working-memory.mdA sticky note for the current task. If a session crashes, the next one picks up from here.
Factsbrain/facts.md, brain/user-profile.mdOne fact per line, each tagged with where it came from.
Journaljournal/YYYY-MM-DD.mdA daily note with check-ins and a short digest of each session.
Promisesbrain/promises.md"Let's come back to that" threads, with due dates. Due ones come up at startup.
Reflectionbrain/reflection-queue.mdThings to think about later, and hunches that aren't facts yet.
Lessonsbrain/mistakes-and-lessons.mdEvery mistake that got corrected, its root cause and the fix that stops it happening again.
Projectslibrary/One note per project or topic, linked from the journal.

Told vs. inferred

Every fact records whether the person said it or Jarvis worked it out. Two made-up examples:

- Likes tea more than coffee — (told, 2026-09-26, chat)
- Prefers answers with the recommendation first — (inferred, 2026-09-28, chat)

Inferred facts count for less. One observation isn't a pattern: a single sighting goes into the reflection queue as a watch: line and becomes a fact only after it's seen again or confirmed. When a new fact contradicts an old one, the old line is replaced and the change is noted, so two conflicting facts are never both active. Git keeps the old version.

04A day with Jarvis

  1. StartOpen Claude Code in the folder. The startup hook hands Jarvis the context, and its first reply mentions anything unfinished or due, in a line or two, and then gets on with what you asked.
  2. WorkAfter each meaningful step, Jarvis updates its working-memory note. New facts and promises are written down as they come up. Before asking you something, it searches its memory first.
  3. WrapSay you're done and /wrap runs: it writes a digest of the session to the journal, updates facts, promises and the dashboard, clears the sticky note, rebuilds the search index and commits.
  4. Between sessionsA morning check-in reviews the calendar and what's due. An evening run works through the idea inbox (see below).

05The idea factory

Drop an idea in, even a one-liner from your phone, and stop thinking about it. At 18:00 the evening run picks up each new idea. A small, cheap model researches it, a mid-sized model drafts a plan, and Jarvis writes it up with a recommendation: approve, trial first, reject or dig deeper. An overnight run catches anything added later, so it's all waiting in the morning.

The line Jarvis doesn't cross. It thinks about ideas unprompted, but it doesn't act on them. Nothing gets built until the owner says yes, and a yes covers only what was shown.

06Safety rails

An agent with write access to its own memory can destroy it. (In the thread that inspired Jarvis, someone's assistant deleted 110 of its own memory files.) Jarvis has two layers of protection:

Hard rules · advisory

At the top of the manual: never delete memory, never rewrite git history, ask before bulk or irreversible changes, check what depends on something before removing it, and treat outside services as read-only.

Permissions · enforced

Claude Code's own settings block or prompt on dangerous commands, whatever the model decides.

LevelExamples
Blockedgit rm, git reset --hard, git push --force, git clean, recursive deletes
Asks firstAny delete, git push, rebase or amend; edits to the settings, hooks, manual or identity
AllowedReading the notes; editing memory folders; search; git add/commit/log; reading the calendar

A separate autonomy policy covers initiative, meaning what Jarvis may do when nobody asked. Keeping memory tidy it just does, and logs. Changes to how it works get drafted for approval. Anything that leaves the PC or is hard to undo is asked about first. When in doubt, the stricter level applies.

Mistakes become rules. When Jarvis gets something wrong, the fix isn't only an apology. It logs the mistake, fixes the damage, finds the root cause and puts a permanent rule where it'll be read. If a written lesson doesn't stop a repeat, the rule becomes a hook that enforces it.

This blog is guarded too. Posts are drafted in the private notes, scanned for names and personal details, and published only after the owner approves them.

07Hooks: rules that can't be forgotten

Most of what makes Jarvis Jarvis is written instructions: the manual, the skills, the lessons. The model reads them and chooses to follow them, and usually it does. But "usually" isn't good enough for everything. Some things have to happen every single time, and some mistakes shouldn't be possible at all.

That's what hooks are for. A hook is a small script that Claude Code itself runs at a fixed moment: when a session starts, when you send a message, just before a command runs. The important part is who runs it. It isn't the model deciding to; it's the software around the model. So a hook fires whether or not Jarvis remembers, agrees or is paying attention.

ToolWho applies itBest for
InstructionsThe model, by reading themJudgement: tone, habits, when to ask, how to write things down
PermissionsClaude Code, before a command runsFlat-out blocking known-dangerous commands
HooksClaude Code, at set momentsThings that must happen every time, and checks too specific for a simple block rule

Jarvis's hooks

  • At startup, a hook hands over today's context: the date, the task in progress, the dashboard, what's due and the last session's summary. Continuity doesn't depend on Jarvis remembering to look.
  • On every message, a hook adds the current time, because the model has no clock. If a session has been sitting open for hours (easy to do from a phone), it refreshes the context too. This one exists because Jarvis once reported a stale picture of the day from a session that had been open since before dawn.
  • Before any shell command, a guard checks for one specific pattern that can freeze the terminal on this PC. The lesson was written down, then broken again the same day. So it became a hook.
When a lesson repeats, it becomes a hook. That's the rule of thumb: judgement stays in writing, but anything that can be checked mechanically and has already slipped once gets enforced. Hooks also fail open: if one hits something unexpected, it steps aside rather than blocking the session.

One thing learned while writing this: a hook can only talk to the model at certain moments. At startup and on each message, whatever the hook prints goes into the conversation. At most other moments it's only shown in the log. So one of Jarvis's hooks, a "save your notes" reminder before long conversations get compressed, most likely never reached Jarvis at all. It's on the list to test. What actually protects the current task there is the startup hook running again and reloading the notes.

08Build your own

The easiest route is to let Claude Code build it with you. That's how Jarvis was made. You'll need:

  • Claude Code and a Claude account
  • Git, and Node.js for the search tool
  • Obsidian (optional; it's just a nice way to read the notes)

Make an empty folder, open Claude Code in it, and paste this:

I want to turn this folder into a persistent AI assistant with memory.
Read https://oafernandes.github.io/jarvis-blog/how-jarvis-works.html and build a
version of that architecture here, one step at a time:

1. A CLAUDE.md operating manual with hard rules (never delete memory,
   never rewrite git history, ask before bulk changes) and an identity
   file. Ask me what to call the assistant and how it should sound.
2. The memory files: working memory, facts (told vs. inferred),
   promises, a journal folder, a reflection queue, mistakes & lessons.
3. A SessionStart hook that prints today's context, and a /wrap skill
   that writes a session digest, updates memory and commits to git.
4. Permission rules in .claude/settings.json that block destructive
   git and delete commands.
5. Optional, ask me first: QMD local search, scheduled check-ins,
   an idea inbox with an evening research run.

Explain each step before you do it, and don't move on until I say so.

Then use it for a week. Tell it things, let it make mistakes, and have it write down what it learns. The shape of the notes matters more than any clever tooling.

Don't copy someone's vault. A memory folder's git history holds every memory it ever had. Start your own from empty and bring over only the machinery (manual, hooks, skills), never another person's journal or facts.
